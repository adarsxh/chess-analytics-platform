# Data Model

> **Status:** V1 design approved 2026-11-13. Implemented through Alembic migrations;
> this document describes intent and guarantees, and the migrations are the source of truth
> for exact DDL. Reasoning for each choice: ADR-014 … ADR-019 in [DECISIONS.md](DECISIONS.md).

## 1. Layers and Postgres schemas

| Schema | Layer | Contents | Versioning |
|---|---|---|---|
| `raw` | Raw | Source payloads as received, fetch log, ingestion runs | **Append-only versions**; payloads never modified |
| `core` | Processed | Canonical, platform-neutral players, games, moves | **Current state**, rebuildable from `raw`; lineage via `raw_game_id` + `parser_version` |
| `analysis` | Analysis | Engine configs, evaluations, classifications | **Versioned** per engine config and classifier version |
| `ops` | Operations | Job queue | Operational state only; no domain lineage points here |

         │ player_id                                 │ raw_game_id (lineage)
 ┌───────▼─────────────────── core ──────────────────▼─────────────────────────┐

## 3. Conventions (all tables)

- Primary keys: `id bigint GENERATED ALWAYS AS IDENTITY`. Natural keys are enforced as `UNIQUE`.
- Column order: `id` first, `created_at`/`updated_at` last (Postgres column order is permanent).
- Foreign key columns have the same type as the key they reference (checked by a unit test).
- Time: `timestamptz`, always UTC. `created_at` on every table; `updated_at` where rows change.
- Fixed value sets: `text` + `CHECK (col IN (...))`, never native `ENUM`.
- Names: `snake_case`, plural tables; constraint and index names generated by a SQLAlchemy
  naming convention, so that Alembic can address them.
- Strings: `text`. JSON: `jsonb`.
- Foreign keys: `RESTRICT` by default; `CASCADE` only from a parent to its own children within a
  layer. Cross-layer FKs are always `RESTRICT`.
- No soft deletes in V1.
- `platform` values: `'chesscom'` (V1). Every natural key includes `platform`.

| error | text, nullable | Run-level failure (e.g. HTTP) |

|---|---|---|

| new_versions_stored | integer | |

**`raw.raw_games`**: one row per distinct version of a game's source payload.

| Column | Type | Notes |
|---|---|---|
| id | bigint PK | |
| platform | text | |
| platform_game_id | text | Chess.com: game `uuid` |
| content_hash | text | SHA-256 of canonical JSON (sorted keys) |
| payload | jsonb | The game object exactly as received |

### 4.4 `ops`

**`ops.jobs`**: generic Postgres-backed queue (ADR-003, ADR-018).

| Column | Type | Notes |
|---|---|---|
| id | bigint PK | |
| job_type | text | `sync_player` \| `analyse_game` |
| payload | jsonb | Job parameters |
| status | text | `queued` \| `running` \| `succeeded` \| `failed` |
| priority | smallint | Lower runs first; on-demand analysis is placed ahead of auto-analysis |
| attempts, max_attempts | smallint | |
| run_after | timestamptz | Retry backoff |
| locked_by, locked_until | text, timestamptz, nullable | Lease; expired lease = reclaimable |
| dedup_key | text, nullable | e.g. `sync:chesscom:<player_id>`, `analyse:<game_id>:<config_id>` |
| last_error | text, nullable | |
| created_at, started_at, finished_at, updated_at | timestamptz | |

Partial `UNIQUE (dedup_key) WHERE status IN ('queued','running')`; claim index
`(priority, run_after) WHERE status = 'queued'`; lease-recovery index `(locked_until) WHERE status = 'running'`;
`CHECK (status <> 'running' OR locked_until IS NOT NULL)`: a running job always holds a lease.

## 5. Guarantees and what enforces them

Every guarantee below is proven by an integration test in
`tests/integration/test_data_model_guarantees.py`, which runs against the real migrations on every
PR. Each test asserts the **specific named constraint** that must fire.

| Requirement | Enforced by |
|---|---|
| A game is never duplicated, even when both players are tracked | `UNIQUE (platform, platform_game_id)` on `core.games` |
| Raw data preserved | Append-only `raw.raw_games`; a new row only when the content hash changes |
| Incremental ingestion | `archive_fetches.etag` → `If-None-Match` → HTTP 304 |
| Idempotent processing | Upsert on game key; `games` + `game_players` + `game_moves` in one transaction |
| Lineage | `games.raw_game_id` + `parser_version`; `raw_games.source_fetch_id` → `archive_fetches` → `ingestion_runs` |
| Reprocessing | `core` rebuilt from `raw`; failures recorded per parser version |
| Analysis separate and versioned | `analysis` schema; `UNIQUE (game_id, analysis_config_id)`; classifier versions |
| Stale analysis detectable | `game_analyses.moves_hash` ≠ `games.moves_hash` |
| Expensive results protected | Cross-layer FKs `RESTRICT` |
| No duplicate concurrent jobs | Partial unique `dedup_key` |
| Separate failure domains | `ingestion_runs.error` · `processing_failures` · `game_analyses.error` |
| Multi-platform / multi-user ready | `platform` in natural keys; players ≠ users; `tracked_players` |

## 6. Key flows

**Sync a player** (`sync_player` job):
1. Create an `ingestion_runs` row.
2. For each archive, send `GET` with the stored ETag and log the request in `archive_fetches`.
3. On 200, for each game: compute the canonical hash and insert into `raw_games`. If that exact
   version already exists, update its `last_seen_at`.
4. Process the new current versions into `core` (one transaction per game). Record failures in
   `processing_failures`.
5. Enqueue analysis for the latest N games (deduplicated).

**Needs processing:** a game whose current raw version ≠ `games.raw_game_id`, or whose
`games.parser_version` < the current parser version. This is derived by query, not by a flag.

**Re-analysis with a new engine:** insert a new `analysis_configs` row and enqueue
`analyse_game` per game. New `game_analyses` rows are created; old ones remain for comparison.

## 7. Source facts (profiled 2026-11-12 on 2,413 real games)

- `rating` per side is the **post-game** rating (rating change matched the game's own result
  in 118 of ~120 consecutive pairs; it matched the previous game's result in 60).
- Game identity: `uuid`, plus a numeric ID inside `url`. Player identity in games: `uuid`.
  The profile endpoint exposes only a numeric `player_id`.
- PGN carries `[%clk]` on every move; `ECO` header always present; `accuracies` on ~12% of games.
- Variants appear rarely (1 `oddschess` with a custom start position). Daily time controls look
  like `1/86400`.
- Result codes seen: win, resigned, checkmated, abandoned, timeout, stalemate, repetition,
  insufficient, timevsinsufficient, agreed, 50move.
- `If-None-Match` with the ETag returns 304; `Last-Modified` is unreliable.

## 8. Planned evolution (not in V1)

- MultiPV ≥ 2 for "only move" detection: a new config only; `pv_rank` already exists.
- Own opening classification (cross-platform): a derived, versioned addition.
- `users` and a user ↔ tracked player relationship (V4).
- Parquet/DuckDB/Delta exports of `core` and `analysis` (V6).
